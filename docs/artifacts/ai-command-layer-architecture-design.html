1Overview & goals

The command layer turns GeoView — a Qt desktop application for seismic interpretation — into something a machine can operate and inspect. Instead of clicks and windows, capabilities are exposed as named commands that take arguments and return structured JSON.

Three consumers share one command set: a person (via a one-shot CLI or an in-app chat), an AI agent (via tool calls), and the unit-test suite. Because every command answers in data rather than pixels, an AI can not only drive the software but verify the result of a change — the property the whole design optimizes for.

2Design principles

  • GUI-free core. All command logic lives in a pure C++14, std-only library (hrs/cli) with no Qt dependency, so it is unit-testable and reusable.
  • Depend on seams, not the app. The library reaches GeoView only through two abstract interfaces; the live implementations live in the GUI module, and tests use mocks.
  • Results are structured data. Every command returns machine-readable JSON — the "oracle" an AI (or a test) can assert against.
  • Read-only by default; writes stay human-gated. Commands query and analyze; anything that would change project data (e.g. running a filter) only opens a dialog for a person.
  • Determinism over guessing. Common intents route to commands in code, so behavior does not hinge on a small model choosing the right call.
  • Local-first. The default LLM backend is on-device; project data stays on-prem unless a remote backend is explicitly enabled.

4Core library abstractions

Five small types carry the whole model. Everything below is std-only and Qt-free.

HrsCliCommand — the unit of behavior

An abstract base identified by a dotted name and described by a JSON Schema, so an LLM can issue it as a tool call without hardcoding flag layouts:

class HrsCliCommand {
  virtual std::string  name() const = 0;         // "volume.stats"
  virtual std::string  description() const = 0;  // one-line synopsis
  virtual std::string  jsonSchema() const = 0;   // draft-07 param schema
  virtual bool         isWriteOperation() const { return false; }
  virtual HrsCliResult run(const HrsCliArgs& args) = 0;
};
  • ProjectCommandBase holds a non-owning IProjectDataSource* and exposes source(); commands needing display also hold an ISeismicViewer*.
  • HrsCliCommandRegistry — a process-wide singleton: registerCommand (idempotent — rejects duplicates, so the CLI runner and the chat dialog safely share one set), dispatch(name, args) → HrsCliResult, and listCommands().
  • HrsCliArgs — parse(tokens) handles --key value, bare --flag, and positionals; typed getters (getString/getInt/getDouble/getBool/hasValue).
  • HrsCliResult — ok(json) / userError(msg,hint) / systemError(msg); serializes via toJsonDocument() and carries an exitCode().
  • HrsCliJsonIO — dependency-free JSON writing (quote, makeObject, makeArray).

5The interface seams

The core never touches Qt or GeoView types. It talks to two abstract interfaces; the GUI module provides the live implementations, and unit tests provide in-memory mocks.

SeamPurposeRepresentative methods
IProjectDataSourceRead/analyze project data (Qt-free structs in, out) loadProject · currentProject · wells · volumes · horizons · wellDetail · volumeStats · wellLogStats · volumeSpectrum · gatherQc · volumeCompare · volumeAutocorr · agcEnvelope
ISeismicViewerDisplay / imaging / open process dialogs showVolumeInline · renderVolumeInline · captureWindow · openBandpassDialog

The GeoView implementations translate these to real internals: HrsCliGeoViewDataSource uses HrsProjectHandler, MergedWellControlSystem (wells/logs), and DataVolumeFactory::dynamicLoad + GeometryInfo (volume geometry/stats, no GUI needed); HrsCliGeoViewSeismicViewer drives HrsQtSeisView for sections, grab().save() for PNGs, and the process framework for real filter dialogs.

Each seam method takes and returns a plain, Qt-free struct — e.g. VolumeStats, WellLogStats, VolumeSpectrum, GatherQc, VolumeCompare, VolumeAutocorr, AgcEnvelope, SeismicRenderResult. The struct is the contract between the two modules: the core marshals it to JSON, the mock reproduces it in memory, and the analysis math lives on the GeoView side where the data actually is. Adding a capability is therefore usually "one struct + one seam method + one command," and the AI layer is untouched (see §11).

Why a seam and not a direct call? The seam is what makes the core GUI-free and testable, lets one command work from CLI / chat / AI unchanged, and keeps the blast radius of a GeoView change on one side of a small interface.
What the seam hides — real data-access constraints. The abstraction earns its keep because the GeoView side is full of sharp edges the core must never see:
  • Exact volume scans read every sample through getTraceBySequentialBinNumber, which works for all volume types — the base getSlab is a stub that only returns data for CDM/HDF5/poststack, so classic .vol volumes would silently read nothing.
  • The classic .vol Bin convention is fixed — row = xline, col = inline, independent of the view layer — which is what lets a region window filter robustly by inline/xline during a sequential scan.
  • Amplitude getters from the .inf header are a fast estimate and can differ from real samples by ~100× (and the RMS estimate is often 0), so --exact forces a full scan.
  • Derived / inverted volumes enumerate via list volumes but only base .vol volumes resolve a path for dynamicLoad; a prestack angle gather yields very few live traces through the sequential accessor, so decon/AGC widen their scan.

6Frontends & entry points

All three reach the same registry; they differ only in how a request becomes a dispatch() call.

FrontendHow a request arrivesWhere results go
One-shot CLI--cli <phrase> --flags parsed by the SessionRunnerJSON to --out file (+ console if attached)
In-app chatNatural language → deterministic route or LLM tool-callStreamed into the chat transcript
AI tool callModel emits {"command":..,"args":..}JSON fed back to the model
One subtlety. The CLI runner maps a two-word phrase to a command but does not map a bare positional to the primary argument — so direct use needs explicit flags (--volume X). The chat parser (§8) does map a positional, which is why stats volume AG_Spec_Bal works in chat but the CLI wants stats volume --volume AG_Spec_Bal.

7The --cli runtime

HrsCliSessionRunner is the one-shot entry. Key mechanics:

  • It is a mode of the GUI binary, not a separate headless program: it does a full GeoView start, then fires the command from a QTimer callback — so the data subsystems are initialized and usable.
  • resolveCommand() first matches a two-word phrase table (open project→project.open, stats volume→volume.stats, …), otherwise treats the first token as a dotted command name.
  • needsLoadedProject() gates query commands; begin() loads the project (if --dir/--name given) before dispatch.
  • emitJson() writes the result to --out (the reliable channel — a GUI-subsystem process has no console of its own) and best-effort attaches to the parent console. Artifact-producing commands (render, help.index, screenshot) keep --out for the artifact and route JSON to a default file.
  • Exit policy: open project and show seismic stay interactive (they need a window); every other command writes its result and exits.

8The AI layer

HrsQtAiAssistantService turns natural language into command calls along two paths that coexist.

(a) Deterministic routing — no model decision

  • Open-project: a regex lifts a .prj path → dir/name → dispatch project.open.
  • How-to / documentation: phrasing like "how do I…" routes straight to help.ask (RAG, §10).
  • Direct commands via HrsCliChatCommandParser::parseChatCommand: a route table of two-word phrases + a primary arg (stats volume AG_Spec_Bal → volume.stats {volume}); multi-arg commands take explicit flags, a bare value falls through to the LLM. On a hit it dispatches immediately and seeds the transcript with the tool call + result, so the model only summarizes.

(b) LLM tool-use loop — free-language fallback

The system prompt lists the commands and the exact call shape; the loop is:

reply = llm(messages)
cmd, args = extractToolCall(reply)   // strict {...} parse, regex fallback
if cmd:
    result = registry.dispatch(cmd, args)
    messages += [assistant(reply), user("Tool result: " + result)]
    // loop, up to myMaxToolCalls
else:
    return reply                     // natural-language answer

extractToolCall parses the first balanced {...}, with a regex fallback for small models' malformed JSON.

(c) Async & streaming

The GUI path is a signal-driven state machine (startMessage → onLlmReply / onLlmDelta). Only the LLM network wait is async — command dispatch stays on the main thread because commands may build Qt widgets. Streamed fragments are sniffed on the first non-whitespace character: a leading { or code fence marks a tool-call turn and is suppressed from the UI; anything else streams live via an answerDelta signal.

(d) Performance & backends

  • Slim summarizer prompt: when the parser already dispatched a command, the model only needs to narrate the JSON, so a short prompt (no command list) is used — far less prefill.
  • keep_alive: Ollama requests carry keep_alive: "30m" to avoid the multi-GB cold reload between messages.
  • Backends: local Ollama by default; Claude is opt-in (GEOVIEW_LLM_PROVIDER=claude + ANTHROPIC_API_KEY). Config layers defaults → environment → QSettings; the API key is read from the environment only and never persisted.

9The LLM client

HrsQtLocalLlmClient speaks to both providers over Qt Network.

  • Ollama /api/chat: with stream:true it parses newline-delimited JSON incrementally, emitting a delta per fragment and the full text on finish:
// one JSON object per line
{"message":{"content":"He"},"done":false}
{"message":{"content":"llo"},"done":false}
{"message":{"content":""},"done":true}
  • Claude /v1/messages (raw HTTP — no official C++ SDK): the system role is lifted to the top-level system field; sends x-api-key + anthropic-version; parses content[] text blocks. Kept single-shot.
  • Embeddings /api/embeddings (default nomic-embed-text) — always via Ollama, even when chat uses Claude (Anthropic has no embeddings API).

10Help RAG

HelpRagService answers documentation questions with citations.

  • Index: iterate *.htm → strip to text → ~800-char chunks → embed each → a JSON-Lines index of {source, text, vec}. Chunks the embedder rejects are skipped, not fatal.
  • Ask: embed the query → cosine top-k → feed the excerpts to the chat model → return the answer plus the cited source pages. Exposed as help.index / help.ask; the chat dialog preloads an index from GEOVIEW_HELP_INDEX.
Scale. The full help corpus — 967 documents — indexes to 5042 chunks in ~6 min (a fault-tolerant build that skips odd/empty chunks rather than aborting), and answers questions the small 20-document subset could not (e.g. "how do I import a SEGY volume" retrieves the right data-load pages).

11Parameter-suggestion pattern

Processing-parameter advice (Bandpass, scaling, deconvolution, AGC, gather conditioning) all follow one reusable recipe:

  1. a read-only analysis command that measures a real feature of the data (e.g. volume.spectrum averages per-trace amplitude spectra);
  2. a transparent rule baseline that turns that measurement into starting parameters (e.g. the −6 dB band → a Bandpass trapezoid);
  3. the LLM layer, reused unchanged — the command description is enough for the model to call it, and the answer always carries a "starting point, review with a geophysicist" caveat.

The same three steps have now been applied five times. Only steps 1–2 are new each time; the AI layer (step 3) is never touched:

ProcessAnalysis commandMeasured featureRule baseline (suggestion)
Bandpass filtervolume.spectrumAveraged per-trace amplitude spectrum; peak, −3/−6 dB band edges, Nyquist Trapezoid from the −6 dB band: low-cut = low·0.5, high-cut = min(high·1.25, Nyquist)
Gather conditioninggather.qcFold, offset/angle range, empty-bin coverage Low fold → super-gather; coverage gaps → infill / regularization; far range → mute (check NMO stretch)
Amplitude scalingvolume.scalingRMS amplitude (from volumeStats, --exact) scaler = target_rms / current_rms (default target 1.0)
Deconvolutionvolume.deconAveraged normalized trace autocorrelation (lag 0…N) Gap = first ACF zero crossing; operator length where |ACF| decays below 0.1; white noise 1%
AGCvolume.agcPer-segment RMS amplitude envelope down the trace Window ≈ 2× half-decay time, clamped [200, 1000] ms; gain type rms

Adding a new process needs only the first two rows-worth of work; the AI layer is untouched. Suggestions are never applied automatically. Where a real processing dialog exists (Bandpass), a command opens GeoView's own dialog for the user to run — the write action stays human.

12End-to-end data flow

A · One-shot CLI — --cli stats volume --volume AG_Spec_Bal --dir … --name … --out r.json

1
GeoView starts in --cli mode; a QTimer fires begin().
2
resolveCommand → volume.stats; project is loaded from --dir/--name.
3
Registry dispatch → the command calls source()->volumeStats().
4
Data source runs dynamicLoad + a scan; returns a plain stats struct.
5
HrsCliResult JSON is written to r.json; the process exits.

B · Chat command — user types bandpass volume AG_Spec_Bal

1
The parser recognizes the phrase → bandpass.dialog {volume} (no model needed).
2
The command computes a Bandpass suggestion via volumeSpectrum, then calls viewer->openBandpassDialog.
3
The viewer reuses GeoView's own launch path — triggers the real "Bandpass Filter" menu action (deferred to the event loop).
4
GeoView's real process dialog opens for the user; the JSON (suggested values + "nothing was run") returns to the chat, and the model narrates it.

13Testing & build

  • Test-driven: 178 unit tests across 29 suites; commands and the phrase parser were written test-first, exercised through mock seams — no GUI required.
  • Verified on real data: exercised end-to-end on the GOM V3 survey (4 wells, 18 volumes, 7 horizons), not synthetic fixtures.
  • Build: the canonical build script sets up the toolchain; adding source files requires a full reconfigure so a new command registers, while edits to existing files build incrementally.
Build gotcha worth knowing. Because command registration happens at link time, building a new source file with the incremental fast-path leaves the command compiled into the library and passing its unit tests, yet reported as "unknown command" in GeoView — the link silently reused a stale project. The rule: after adding files, do one full reconfigure build first, then incremental builds are fine.

14Design decisions & tradeoffs

DecisionWhyTradeoff
GUI-free core behind seamsTestable, reusable across frontendsExtra indirection; each capability needs a seam method
Structured JSON resultsAn oracle an AI/test can assert onHand-written JSON; schemas to maintain
Deterministic phrase routingReliable dispatch independent of model qualityA route table to keep in sync with commands
Read-only + human-gated writesSafe to put in front of real data / an autonomous agentThe AI can suggest and open, not apply
--cli as a GUI modeReuses the app's data subsystems as-isEvery command briefly starts the app (a window flashes)
Local-first LLMProject data stays on-prem by defaultSmall local models route tool calls less reliably than large/remote ones
