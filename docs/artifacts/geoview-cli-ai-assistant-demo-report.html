CLI & AI Assistant for GeoView

A scriptable command layer and an in-app AI assistant for the seismic interpretation suite — built as a thin shell over existing C++ libraries, with one command registry shared by the CLI, the chat dialog, and (later) Python.

branch feature/cli-foundation ✓ 142 unit tests pass ✓ verified on GOM V3.prj C++14 · Qt · Ollama / Claude
01

What was built

The work exposes GeoView's key read-only operations as scriptable commands and connects an AI assistant to that same surface. The architectural decision underneath everything: one registry, three frontends. A command is written once and reached identically from the CLI, the in-app chat, and the future Python binding — so behaviour can never drift between them.

Every command shipped so far is read-only. AI parameter suggestions are advisory, carry a "review by a geophysicist" caveat, and are never auto-applied — consistent with the no-autonomous-changes policy. The default LLM backend is a local Ollama model, so project data stays on the workstation unless a user explicitly opts into the Claude backend.

Layer 1 Existing C++ libraries — WellControlSystem, SeismicVolume, process chains. Unchanged.
Layer 2 Command registry (hrs/cli/, GUI-free) — HrsCliCommandRegistry + the IProjectDataSource / ISeismicViewer seams. Fully unit-tested against a mock.
Layer 3 AI assistant service — HrsQtAiAssistantService runs a tool-use loop over the registry; HrsQtLocalLlmClient talks to Ollama or Claude (async, non-blocking UI).
Layer 4 Frontends — geoview --cli … for scripting, the in-app chat dialog, and semantic Help Q&A (RAG over the help docs).

03

Demo setup

Demos run against C:\test\GOM V3.prj (4 wells, 18 volumes, 7 horizons). GeoView is a GUI-subsystem process with no console of its own, so query commands write their JSON to a --out file; the path convention is a trailing slash on --dir and the .prj suffix on --name.

Launch template — start GeoView headless with PowerShell, then read the result file:

PowerShell — launch convention
# geoview is GUI-subsystem; --out is the reliable result channel
PS> $exe = "…\bin\win64\vs2022\hrs\Debug\geoview.exe"
PS> Start-Process $exe -ArgumentList '--cli describe project --dir C:\test\ --name "GOM V3.prj" --out C:\test\out.json'
PS> Get-Content C:\test\out.json

Security & compliance posture

  • Local by default. The assistant uses a local Ollama model; project data stays on-prem. Claude is explicit opt-in and warns before sending data off-machine.
  • No secrets in code. The Claude API key is read only from ANTHROPIC_API_KEY, never hardcoded or persisted.
  • Advisory only. Every AI parameter suggestion is a starting point with a geophysicist-review caveat and is never auto-applied.
  • Read-only surface. No command shipped so far writes to the project.

B · Statistics

B1Volume amplitude stats — estimate vs exact
stats volume
> geoview --cli stats volume --volume AG_Spec_Bal
→ instant estimate from .inf metadata

> geoview --cli stats volume --volume AG_Spec_Bal --exact
→ full scan of 11.88M samples: min -276.7 / max 713.3 /
  mean ~0 / rms 0.78, with p10 < p50 < p90 + histogram
B2Log stats · multi-log compare
stats well / compare logs
> geoview --cli stats well --well Well_1 --log "Gamma Ray"

> geoview --cli compare logs --well Well_1 --logs "GR,Resistivity,Density"
→ side-by-side, correct units: gAPI / ohm·m / g·cc
B3Region-windowed stats
stats volume — region
> geoview --cli stats volume --volume AG_Spec_Bal --inline-min 14700 --inline-max 14750
→ 153,306 samples (vs 11.88M whole-volume); stats narrower as expected

D · AI parameter suggestions — one recipe, five processes

Each command computes a real data feature and a deterministic rule baseline. The AI layer is reused with no extra wiring: the command's own description is enough for the assistant to call it for a parameter question and narrate the numbers — always with the review caveat.

D1Spectrum → Bandpass
spectrum volume
> geoview --cli spectrum volume --volume AG_Spec_Bal
→ 2156 traces, Nyquist 125 Hz, peak ~5 Hz, −6 dB band [2.5, 40]
  suggested Bandpass 1.2 – 2.5 – 40 – 50 Hz  (review caveat)
D2Gather QC → conditioning
gather qc
> geoview --cli gather qc --volume AG_Spec_Bal
→ prestack ANGLE gather: 2–44°, fold 15, full coverage
  (23,715 live traces over 1581 bins) → super-gather / mute hints
D3RMS → scaler
scaling volume
> geoview --cli scaling volume --volume AG_Spec_Bal --exact
→ current_rms 0.78 → suggested scaler 1.28 (target RMS 1.0), scaled_max 914
D4Autocorrelation → predictive decon
decon volume
> geoview --cli decon volume --volume AG_Spec_Bal
→ ACF [1, 0.85, 0.47, 0.05, −0.23, …] → operator 28 ms /
  gap 16 ms / white-noise 1%
D5Envelope → AGC gain window
agc volume
> geoview --cli agc volume --volume AG_Spec_Bal
→ 32-seg RMS envelope (peak seg 24), decay 0.91 → gain window
  200 ms / type rms

F · In-app AI chat

F1Natural language → tool call → answer

How it holds together

  • ▸Seam-based & testable. Commands depend only on IProjectDataSource / ISeismicViewer; a mock backs 142 unit tests with zero Qt/GeoView dependency in hrs/cli/.
  • ▸One reusable AI recipe. Each of the five parameter suggestions = an analysis command (a data feature) + a deterministic rule baseline. The LLM layer is reused verbatim — a new process needs no prompt changes.
  • ▸Honest about the data. AG_Spec_Bal turned out to be a prestack angle gather, not poststack — surfaced by gather.qc, and the reason decon/AGC scan widely for the few live sequential traces.
  • ▸Async assistant. Only the LLM HTTP wait is async; widget-building commands stay on the main thread by design.
